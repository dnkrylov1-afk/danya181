# Квантастика — MVP закрытой базы знаний (первый модуль)

Готовый исходный код для тестового развёртывания, **не опубликован** и **не подключён к рабочему проекту автоматически**.

## Что реализовано

- Вход по логину и паролю (Firebase Authentication использует внутренний технический email-идентификатор, контактная почта сотрудника хранится отдельно).
- Администратор создаёт сотрудника: логин, пароль (вручную или автоматически), ФИО, почта, пол, роль.
- Список сотрудников, обновление профиля/роли, блокировка/разблокировка, сброс пароля.
- Пароли не сохраняются в Realtime Database; показываются администратору один раз после создания или сброса.
- Разграничение прав на создание пользователей серверными Cloud Functions.
- Статьи, 5 категорий шаблонов и статьи по установке/техническим проблемам импортируются в закрытую Realtime Database вместо открытых `.js` файлов.
- Сохранён прежний интерфейс, поиск и просмотр статей, редактирование статей администратором.

## Важно: состояние MVP

Это исходники, а не результат запуска на реальном Firebase. Синтаксис JS проверен локально. Проверки входа, функций, правил безопасности и развёртывания в реальном Firebase **ещё не выполнялись**.

### Серьёзные требования перед релизом

1. **Отключить самостоятельную регистрацию Firebase Authentication на стороне провайдера.** Скрытие формы не запрещает вызов публичного Firebase signup API. Если платформа/тариф не поддерживает прямой запрет через консоль, используйте Firebase Authentication with Identity Platform и blocking function `beforeCreate` с администраторским allowlist/отклонением саморегистрации. Пока это не настроено, посторонние могут создавать неактивные учётные записи Firebase, хотя защитные правила не дают им читать контент; они также могут резервировать желаемые логины. Не открывайте систему в продакшн без решения этого вопроса.
2. **Нельзя публиковать `source-content/` или служебные скрипты.** Firebase Hosting должен публиковать *только* `public/`.
3. **Резервная копия до любых операций**: экспортируйте Realtime Database JSON, сохраните исходники, правила, список текущих пользователей. Применение новых правил может отключить прежний способ входа. Делайте это в отдельном тестовом проекте или с заранее подготовленным аккаунтом администратора.
4. Проверьте, разрешён ли Firebase Blaze и Cloud Functions в компании, настройте лимиты и бюджетные оповещения. Обязательно HTTPS.
5. Роли `senior` и `manager` зарезервированы для последующего модуля отчётов; **сами отчёты ещё не реализованы**. В этом MVP изменять страницы может только `admin`. Остальные читают материалы.
6. Клиентская генерация использует Web Crypto; серверная генерация использует `node:crypto`. Не отправляйте пароли в чат.
7. Firebase Authentication по умолчанию позволяет восстановление доступа через технический email-адрес, поэтому перед выпуском следует отключить неподходящие механизмы восстановления/действия по email в настройках либо перейти на идентификационную архитектуру с явным username-login endpoint и защищённой серверной проверкой. Контактная почта, указанная в анкете, отдельно.

## Порядок настройки в тестовом Firebase

1. Создать отдельный тестовый проект Firebase (рекомендуется), включить Authentication → Sign-in method → Email/Password, Realtime Database и Cloud Functions. Запретить публичную регистрацию см. п. 1 выше. В проекте использовать актуальные Firebase web config и RTDB URL (в `public/index.html`, `functions/index.js`, `scripts/*.cjs`, `.firebaserc`). В комплекте указаны значения, извлечённые из исходного проекта пользователя; замените их при работе в отдельном тестовом проекте.
2. Установить локально Node.js 22, Firebase CLI, выполнить `firebase login` и получить права deploy для тестового проекта.
3. Из каталога `functions/` выполнить `npm install`; из `scripts/` выполнить `npm install`.
4. Для выполнения служебных скриптов на собственном компьютере авторизоваться через Application Default Credentials или задать путь к сервисному ключу в `GOOGLE_APPLICATION_CREDENTIALS` (ключ никогда не отправлять в чат и не помещать в `public/`).
5. **До публикации правил** запустить `node scripts/bootstrap-admin.cjs` из корневой папки, чтобы создать первого администратора. Эта команда отказывается работать, если `/users` уже содержит записи. Сохранить выданный пароль в менеджере паролей.
6. Запустить `node scripts/import-content.cjs`: импортирует отсутствующие статьи и шаблоны; существующие `/pages/*` не перезаписывает.
7. В корне проекта запустить `firebase deploy --only functions,database,hosting --project <TEST_PROJECT_ID>` после проверки конфигурации.
8. Пройти вручную тесты ниже. Только после этого планировать переход на рабочий проект.

## Проверки перед продакшеном

- Пользователь без входа не может читать `/pages`, `/templates`, `/users` из RTDB.
- Вышедший или отключённый сотрудник не может читать содержимое.
- Сотрудник с ролью `teacher` не может создать аккаунт через прямой вызов Cloud Function.
- `teacher`, `senior`, `manager` не могут записывать в `/pages` или `/users`.
- Администратор может создать пользователя и получает его пароль один раз.
- Повторный логин выдаёт ошибку занятости, логин с чужим паролем не работает.
- Изменение роли, блокировка и сброс пароля прекращают старые сессии в соответствии с правилами Firebase (проверьте фактически; для строгого немедленного аннулирования используйте дополнительную проверку server session/revocation).
- Созданная через публичный Firebase signup API учётная запись не должна допускаться политикой регистрации (см. выше).
- Публичные адреса вида `/source-content/data-full.js` не возвращают статьи.
- Статьи, шаблоны и поиск работают после импорта.

## Что НЕ сделано

- Панель отчётов старших преподавателей/руководителя.
- Серверная проверка редакторского HTML и история версий (нужно до допуска большого числа редакторов).
- Сложный WYSIWYG-редактор, админское добавление новых страниц и загрузка видео.
- Запрет саморегистрации на уровне Identity Platform (требуется конфигурация платформы и отдельная blocking function).
- Автоматические интеграционные тесты Firebase Emulator Suite.

## Состав

- `public/` — клиентский сайт.
- `functions/` — серверные Cloud Functions c Firebase Admin SDK.
- `scripts/` — создание первого администратора и импорт данных.
- `source-content/` — исходные материалы (только локально, не публиковать).
- `database.rules.json` — правила безопасности RTDB.
